  What I built. A single stdlib Python script, resy_crawler.py, plus a README
  and the sample output in data/. It made one request to Resy's search endpoint
  and wrote 25 San Francisco venues to CSV and JSON.

  How the API works. The web client authenticates with a public key embedded in
  its JavaScript bundle, sent as a ResyAPI api_key Authorization header with an
  X-Origin header. The venue search is a POST to /3/venuesearch/search. I
  confirmed the request shape by reading the client's own code rather than
  guessing.

  Findings that shape a full crawl later:

  - Page size is capped at 75 by the server, whatever you ask for.
  - Three ways to scope to SF give slightly different sets. Filtering by
    location code returns 149 venues. A bounding box over the city returns 127.
    A 12 km radius returns 129. A complete list should union all three and
    dedupe on venue id, which the script already does per strategy.
  - Without a geo filter the endpoint returns every Resy venue worldwide sorted
    by distance, so that path is not useful for scoping.

  Polite defaults. One request and at most 50 rows unless you pass --max-pages
  and --delay. Total requests for a full SF pull would be about 6, so rate
  limiting is unlikely, but it stays opt-in as you asked.

❯ Let's go back to the busyness score. Currently, it's half-hours with nothing

⏺ Correct, with three qualifiers on how each term is measured.

  - Denominator: the half-hour boxes from the first to the last dinner seating
    for a party of two on that night, inclusive, taken from Resy's "notify me"
    range for the dinner service type. Lunch and brunch windows are ignored.
  - Numerator: boxes with no bookable slot. Slots arrive at 15-minute
    granularity and are rounded down into their half-hour box, so a box counts
    as open if any slot lands in it.
  - Aggregation: that ratio is computed per night, and the score is the plain
    mean over the nights that had a dinner window. Nights without one are
    skipped. Nothing is weighted, normalized against other venues, or tiered
    afterward.

  The code for the per-night part is in resy_busyness/scoring.py, functions
  dinner_boxes and open_boxes, and the mean is in classify.

❯ Ok, the score is hardcoded at ingestion (when we run the scan). Correct? if   
  so, can we make it on the fly based on variables rather than fixed constants?

⏺ Yes. Today the score is fixed at ingestion in two layers, and only the first
  one is truly locked.

  What the run stores. For each venue and night, the pipeline keeps only the
  dinner-derived result: box count, open box count, the open half-hour times,
  and the dinner window string. The raw lunch and brunch windows, the 15-minute
  slot times, and the seating-area tags are read and discarded. So a lunch score
  or a 15-minute grid cannot be recomputed from the current database. Rescoring
  needs a new run.

  What is genuinely an ingestion parameter. Party size and the set of days. Resy
  answers per party size, so a party-of-four score is a separate scan by
  nature. Everything else, including service type, grid step, the inclusive
  last-seating rule, the minimum nights, and the far-out verification threshold,
  is a scoring choice that could be applied at read time if the raw observation
  were kept.

  What changes if we move scoring to query time:

  - Storage grows but stays small. The SCD2 night row would hold every window
    and slot time, a few kilobytes instead of a few hundred bytes. About 1,100
    rows per run, so megabytes, not gigabytes. Versions would also churn
    slightly more, since a lunch slot change would open a new row even when
    dinner is unchanged.
  - Compute is trivial. Scoring 142 venues over 8 nights is under a millisecond
    of Python per request. No caching needed.
  - The results table becomes a cache or goes away. Rank depends on the
    parameters, so the API takes scoring parameters and computes from the states
    as they stood at that run. SCD2 makes this natural: pick the versions valid

  Two points behind that:

  - It is normalized by construction. Each night's ratio divides taken boxes by
    that restaurant's own boxes, so a 9-box counter and a 26-box hall are
    compared on the same scale. Averaging across nights keeps it in 0 to 1. That
    is what the exercise's "normalized scalar" asks for.
  - A second pass would remove information. Percentile ranking or tiering
    against the field, which the original mockup showed, would turn 0.90 into
    "top 5%" and hide how full the book actually is. It would also make a
    venue's number change whenever other venues change, which breaks comparisons
    across snapshots.

  explicit, one sentence there would do: "The ratio is the score. No ranking,
